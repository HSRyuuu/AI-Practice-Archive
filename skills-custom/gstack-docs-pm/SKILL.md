# gstack-docs-pm: 9단계 프로젝트 문서 관리

바이브코딩 환경에서 시니어 PM이 AI와 함께 프로젝트 산출물을 체계적으로 생성·관리하기 위한 문서 관리 방법론이다.

## 문서 루트 결정 (DOCS_ROOT)

gstack 폴더 구조를 생성하기 전에, 프로젝트의 문서 루트 경로를 먼저 결정한다. 이 경로를 이하 `{DOCS_ROOT}`로 표기한다.

**결정 로직 (순서대로 평가):**

```
1. 기존 gstack 구조가 있는가? (01_분석/, 02_설계/ 등 번호 폴더 존재 여부)
   ├── docs/ 에만 있음  → DOCS_ROOT = docs/
   ├── .docs/ 에만 있음 → DOCS_ROOT = .docs/
   ├── 둘 다 있음       → 기존 구조가 있는 쪽을 사용
   └── 없음 → 2번으로

2. docs/ 와 .docs/ 중 어떤 폴더가 존재하는가?
   ├── docs/ 만 있음    → DOCS_ROOT = docs/
   ├── .docs/ 만 있음   → DOCS_ROOT = .docs/
   ├── 둘 다 있음       → 사용자에게 질문: "docs/와 .docs/ 둘 다 존재합니다. 어디에 gstack 문서를 관리할까요?"
   └── 둘 다 없음 → 3번으로

3. 폴더가 하나도 없으면
   → 사용자에게 질문: "문서 폴더를 docs/ (git 추적) 또는 .docs/ (git 미추적) 중 어디에 만들까요?"
```

> **참고**: `docs/`는 git에 포함되어 팀과 공유하기 적합하고, `.docs/`는 `.gitignore`에 추가하여 로컬 전용으로 관리하기 적합하다. 프로젝트 성격에 따라 선택한다.

결정된 `{DOCS_ROOT}`는 이후 모든 경로에서 사용한다. 아래 문서의 `docs/`는 모두 `{DOCS_ROOT}`를 의미한다.

## 핵심 원칙

1. **문서가 코드의 컨텍스트다** — AI 세션이 바뀌어도 문서가 의사결정 맥락을 유지한다
2. **단계별 산출물 → 다음 단계의 입력** — 분석보고서가 설계의 근거, 설계서가 개발의 명세가 된다
3. **`.md`가 주인공, 나머지는 `references/`** — 마크다운은 단계 루트에, 기타 포맷은 references/ 하위에 관리한다
4. **문서-코드 동기화** — 커밋 시 `docs:` prefix로 문서 변경을 추적한다

## 템플릿

각 단계별 산출물 템플릿은 `assets/templates/` 에 위치한다. 문서 생성 시 해당 템플릿을 Read하여 `{프로젝트명}`, `{YYYY-MM-DD}` 등 플레이스홀더를 치환한다.

### 생성 모드

| 모드          | 설명                                                           | 파일명 패턴          | 예시                              |
| ------------- | -------------------------------------------------------------- | -------------------- | --------------------------------- |
| **새 파일**   | 건별로 독립 파일 생성. 시점·주제마다 스냅샷이 남아야 하는 문서 | `YYYYMMDD_{내용}.md` | `20260328_현행시스템_종합분석.md` |

## 사용 시점별 액션

### 1. 프로젝트 초기화 (`docs init`)

사용자가 "docs 초기화", "문서 구조 만들어줘", "gstack init" 등을 요청하면:

1. **DOCS_ROOT 결정**: 위의 "문서 루트 결정" 로직을 수행한다
2. **폴더 생성**:

```bash
mkdir -p {DOCS_ROOT}/{01_분석,02_설계,03_계획,04_개발,05_시험,06_검증,07_배포}/references {DOCS_ROOT}/08_버전관리/changes {DOCS_ROOT}/09_이슈
```

3. **README 생성**: `assets/templates/README.md` 템플릿을 Read하여 `{DOCS_ROOT}/README.md`를 생성한다

### 2. 단계별 산출물 생성

사용자가 특정 단계의 문서를 요청하면:

1. 해당 단계의 템플릿 파일을 `Read`한다
2. 플레이스홀더를 치환한다: `{프로젝트명}`, `{YYYY-MM-DD}`, `{주요 기술}` 등
3. 프로젝트 컨텍스트(분석 결과, 설계 결정 등)를 반영하여 내용을 채운다
4. 파일 배치 규칙에 따라 적절한 위치에 생성한다

**파일 배치 규칙:**

- `.md` 파일 → 단계 폴더 루트 (예: `docs/02_설계/기술설계서.md`)
- `.html`, `.pptx`, `.xlsx`, `.json`, `.py`, 이미지 등 → `references/` 하위 (예: `docs/02_설계/references/목업.html`)

**파일 네이밍 규칙:**

```
{프로젝트약칭}_{기능명}_{문서유형}_{YYYYMMDD}.{ext}
```

- 날짜는 최초 작성일 기준
- 버전이 필요하면 `_v1.0`, `_v2.0` suffix 추가

### 3. 단계 완료 시 README 갱신

각 단계의 산출물이 완성되면 `docs/README.md`의 상태를 갱신한다:

| 상태 표기           | 의미                     |
| ------------------- | ------------------------ |
| `-`                 | 미착수                   |
| `작성중`            | 진행 중                  |
| `완료 (YYYY-MM-DD)` | 완료                     |
| `갱신 필요`         | 코드 변경 후 문서 미반영 |

### 4. 배포 시 08\_버전관리 갱신

배포가 완료되면:

1. `08_버전관리/RELEASE_NOTES.md` 상단에 새 버전 블록을 추가한다
2. `08_버전관리/changes/YYYYMMDD_vX.Y.Z.md` 파일을 새로 생성한다
3. 변경기록 템플릿(`assets/templates/08_버전관리_변경기록.md`)을 Read하여 플레이스홀더를 치환한다

### 5. 작업 완료 시 09\_이슈 기록

기능 개발, 버그 수정, UI 개선 등 의미 있는 작업이 완료되면:

1. 이슈 타입에 맞는 그룹 템플릿을 Read한다:
   - 기능추가, UI개선, 스타일, 데이터 → `assets/templates/09_이슈_변경.md`
   - 버그수정 → `assets/templates/09_이슈_버그.md`
   - 문서화, 테스트 → `assets/templates/09_이슈_기록.md`
2. frontmatter의 플레이스홀더를 치환하고, 본문에 작업 내용을 채운다
3. `09_이슈/YYYYMMDD_{이슈타입}_{제목}.md` 경로에 생성한다

## 단계 간 연결 (Traceability)

각 문서는 이전 단계의 산출물을 **명시적으로 참조**해야 한다:

```
01_분석 → "13건 문제 도출"
   ↓
02_설계 → "문제 #1 → SSR/ISR 설계"
   ↓
03_계획 → "설계서 기반 페이지 우선순위 배정"
   ↓
04_개발 → "계획서 Sprint 1 기준 구현"
   ↓
05_시험 → "개발 완료 기능 기준 시나리오"
   ↓
06_검증 → "테스트 결과 + 성능 기준 판정"
   ↓
07_배포 → "검증 통과 버전 배포"
   ↓
08_버전관리 → "배포 버전별 변경 기록"
   ↓
09_이슈 → "개별 작업 단위 기록 아카이브"
```

문서 서두에 참조를 명시한다:

```markdown
**근거 문서**: `01_분석/종합분석보고서.md` 2.2절 문제점 #1, #4
```

## git 커밋 규칙

```

```

예시:

docs: 09_이슈 버그수정 인증토큰만료 기록
```

## 문서 건강도 체크 (`docs status`)

사용자가 "문서 현황", "docs status" 등을 요청하면:

1. **완성도**: 9단계 중 산출물이 존재하는 단계 수
2. **최신성**: 마지막 수정일이 코드 마지막 커밋일보다 오래된 문서
3. **참조 무결성**: references/ 내 파일이 .md에서 참조되고 있는지
4. **README 동기화**: `docs/README.md`의 상태가 실제와 일치하는지

출력 형식:

```
문서 건강도 체크
