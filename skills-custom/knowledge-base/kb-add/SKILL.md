# KB Add — 새 지식 추가

어디서든 호출 가능한 전역 스킬. 사용자가 제공한 구체적 내용을 Knowledge Base에 추가한다.

> **핵심 원칙**
> 1. LLM 자체 지식 생성 금지 — 사용자가 제공한 구체적 사실/경험/데이터만 다룬다.
> 2. 배치 전 반드시 대상 경로 컨펌 — "→ {경로}에 추가하겠습니다. 확인?"

---

## Step 0. 볼트 경로 확인 + 스키마 로드

1. `~/.config/kb/config.json`을 읽어 `kb_root` 경로를 확인한다.
2. 파일이 없거나 `kb_root`가 없으면 사용자에게 볼트 경로를 물어본 뒤 저장한다.
3. `{kb_root}/SCHEMA.md`를 읽어 폴더 구조, 배치 규칙, Group 정의를 로드한다.
4. `{kb_root}/.claude/CLAUDE.md`를 읽어 frontmatter 컨벤션을 확인한다.
5. 없으면 에러: **"`/kb-setup`을 먼저 실행하세요."**

---

## Step 1. 입력 감지 + 분기

### 1-1. 입력 타입 판단

| 입력 패턴 | 타입 | 처리 |
|---|---|---|
| `http(s)://...` | `web` | → Step 2A |
| 바이너리 파일 경로 (`.pptx`, `.pdf`, `.xlsx`, `.docx`, `.png`, `.jpg` 등) | `file` | → Step 2B |
| 인자 없음 or `Inbox` 지정 | `inbox` | → Step 2D |
| 그 외 모든 경우 | `default` | → Step 1-2 거부 판단 → Step 2C |

### 1-2. 거부 판단 (default 타입만)

사용자 입력에 **구체적 사실/경험/데이터**가 포함되어 있는지 판단한다.

- **허용**: 회의 내용, 특정 설정값, 프로젝트 결정사항, 경험에서 얻은 지식 등
- **거부**: "파이썬 REST API 개발방법", "Docker 사용법" 등 LLM이 훈련 데이터에서 일반 지식을 생성해야 하는 요청

거부 시:
> "구체적인 내용이나 출처를 제공해주세요. LLM이 일반 지식을 생성하는 것은 이 KB의 정책에 맞지 않습니다."

---

## Step 2. 타입별 처리

### 2A. 웹 링크

1. URL을 파싱하여 마크다운으로 변환한다 (defuddle 스킬 또는 WebFetch 사용).
2. 파싱 결과를 `{kb_root}/raw/{slug}.md`에 저장한다.
3. 파싱된 내용을 기반으로 정리된 문서를 생성한다.
4. → Step 3 (배치 판단)

### 2B. 외부 파일 (바이너리)

1. 원본 파일을 `{kb_root}/raw/{파일명}`에 복사한다.
2. 내용을 추출/정리한다:
   - PDF: 텍스트 추출
   - PPTX/DOCX: 텍스트 추출
   - 이미지: LLM이 이미지를 읽고 설명 생성
3. 추출된 내용을 기반으로 정리된 문서를 생성한다.
4. → Step 3 (배치 판단)

### 2C. 구체적 내용 (default)

1. 사용자에게 질문한다:
   > "이 내용을 정리할까요, 그대로 복사할까요?"
   >
   > 1. **정리** — 내용을 분석하여 구조화된 문서로 정리
   > 2. **복사** — 원본 내용 그대로 저장
2. 선택에 따라 문서를 준비한다.
3. → Step 3 (배치 판단)

### 2D. Inbox 정리

1. `{kb_root}/Inbox/` 내 모든 파일을 스캔한다.
2. 각 파일에 대해:
   a. SCHEMA.md를 보고 배치 위치를 판단한다.
   b. "→ {파일명}을 {폴더경로}에 배치하겠습니다. 확인?" ← 개별 컨펌
   c. 승인 시 파일 이동 + frontmatter 삽입
   d. 거부 시 Inbox에 유지
3. → Step 4 (후처리)

---

## Step 3. 배치 판단

1. SCHEMA.md의 폴더 구조와 배치 규칙을 읽는다.
2. 내용을 분석하여 적절한 폴더를 판단한다.
3. **판단 가능**:
   > "→ **{폴더경로}**에 추가하겠습니다. 확인?"
   - 승인 → Step 4
   - 거부 → 사용자에게 경로 질문
4. **판단 불가**:
   > "어디에 넣을까요?"
   - 사용자가 경로 지정 → 해당 폴더
   - 사용자가 모르겠음 → `Inbox/`에 배치
5. **SCHEMA에 없는 새 폴더 필요**:
   > "'{폴더명}' 폴더가 SCHEMA에 없습니다. 새로 만들까요?"
   - 승인 → 폴더 생성 + 00_index_{폴더명}.md 생성 + SCHEMA.md 업데이트
   - 거부 → 기존 폴더 중 선택 요청

---

## Step 4. 후처리

### 4-1. 문서 생성 + Frontmatter 삽입

배치된 문서에 frontmatter를 삽입한다:

```yaml
---
tags: [{내용에서 추출한 태그}]
group: [{폴더 위치에 대응하는 그룹}]
source: "[[raw/{파일명}]]"          # raw에 원본이 있을 때만
created: {오늘 날짜 YYYY-MM-DD}
---
```

### 4-2. raw 원본 연결

raw/에 원본이 저장된 경우, 배치된 문서 하단에 백링크를 추가한다:

```markdown

---
원본: [[raw/{파일명}]]
```

### 4-3. 00_index_{Name}.md 갱신

1. 배치된 폴더의 `00_index_{Name}.md`에 위키링크 + 한줄 요약을 추가한다.
2. 상위 폴더의 `00_index_{Name}.md`에도 반영한다 (필요 시).

추가 형식:
```markdown
| 문서 | 설명 |
|---|---|
| [[{경로/문서명}]] | {한줄 요약} |
```

### 4-4. 교차 참조

배치된 문서의 내용과 관련된 기존 문서가 있으면, 양방향 위키링크를 추가한다.

### 4-5. qmd 인덱스 리빌드

```bash
qmd index rebuild 2>/dev/null || true
```

### 4-6. Git 커밋

```bash
cd {kb_root}
git add -A
git commit -m "kb: add '{제목}'"
```

## 예시

```
# 웹 링크
/kb-add https://example.com/rag-tutorial
  → raw/rag-tutorial.md 저장
  → "→ Common/RAG/에 추가하겠습니다. 확인?"
  → Common/RAG/rag-tutorial-정리.md 생성
  → 00_index_{Name}.md 갱신 + git 커밋

# 구체적 내용 (다른 워크스페이스에서)
/kb-add 프로젝트에 회의록 추가해줘
  [회의 내용 덤프]
  → "이 내용을 정리할까요, 복사할까요?"
  → "→ Work/ProjectA/에 추가하겠습니다. 확인?"
  → 기존 문서에 분산 추가 or 새 문서 생성
  → 00_index_{Name}.md 갱신 + git 커밋

# 일반 지식 (거부)
/kb-add 파이썬 REST API 개발방법
  → "구체적인 내용이나 출처를 제공해주세요."
```
